---

You are a Data Engineer responsible for building and validating a Medallion Architecture that ingests synthetic credit-card source data and consolidates it into a single canonical Gold-layer data model for the credit-card domain, implemented with **dbt on Google BigQuery**.

---

## Architecture Overview

### Bronze Layer

Contains raw, deterministically generated synthetic credit-card data covering **26 business tables** (customers, accounts, credit_cards, transactions, disputes, fraud_alerts, rewards, and related reference/dimension tables).

- Stored in the BigQuery dataset **`acn-uki-ds-data-ai-project.credit_card_synt`** (region: `europe-west2`).
- Generated by `credit_card_synthetic.py`; business columns are retained as their native Python/BigQuery types with no downstream casting or cleansing applied at this layer.
- Serves as the source of truth with minimal transformation; declared in dbt via `sources.yml` as `source('bronze', '<table_name>')`.
- A dedicated **`relationship_definitions`** seed (materialised to `ops`) documents every primary-key/foreign-key relationship (**21 relationships**) and its cardinality.

### Silver Layer (Standardisation & Curation Layer)

- Stored in the BigQuery dataset **`acn-uki-ds-data-ai-project.silver`**.
- Reads each Bronze table 1:1 via `{{ source('bronze', '<table>') }}` (no joins or renames — table and column names match Bronze) and applies **`SAFE_CAST`** to convert raw columns to the target data type defined by `cast_rules` in the mapping sheet.
- Adds standard audit columns: `audit_source_system`, `audit_source_table`, `audit_insert_ts`, `audit_update_ts`, `audit_record_hash` (`TO_HEX(SHA256(TO_JSON_STRING(STRUCT(...))))`), `dq_checked_at`.
- Adds row-level data-quality columns: `dq_error_count`, `dq_errors` (pipe-delimited), `dq_status` (`PASS`/`FAIL`) based on required-column null checks and `SAFE_CAST` failure detection.
- Publishes a dedicated **`silver_relationship_dq_results`** model that LEFT ANTI JOINs every declared child foreign key against its parent primary key to detect orphaned keys across all 21 relationships.
- Never sets a column to null if it is populated in Bronze; nulls only occur where the source Bronze value itself is null or a `SAFE_CAST` genuinely fails.
- All date/datetime columns are converted to `DATE` or `TIMESTAMP` per `cast_rules` (e.g. `transaction_date → DATE`, `audit_insert_ts → TIMESTAMP`).
- Each Silver model follows the standard four-CTE pattern: `bronze → typed → quality → final SELECT`.

### Gold Layer (Canonical Layer)

- Stored in the BigQuery dataset **`acn-uki-ds-data-ai-project.gold`**.
- Creates **six business-ready canonical entities** by joining and aggregating Silver tables:
  - `gold_customer_360`
  - `gold_transaction_360` *(partitioned by `transaction_date` DAY; clustered by `customer_id`, `merchant_id`)*
  - `gold_merchant_performance`
  - `gold_account_financial_summary`
  - `gold_fraud_case_360`
  - `gold_rewards_engagement`
- This implementation is currently single-source. If additional source systems are onboarded in future, equivalent entities from each source must be unioned only when they share **identical column names, identical column order, and compatible data types**.
- Adds standard audit and lineage columns to every entity: `gold_entity_name`, `gold_created_ts`, `gold_record_hash` (`TO_HEX(SHA256(TO_JSON_STRING(STRUCT(...))))`).
- Delivers a single harmonised version of each business entity, validated by the Gold data-quality report and the medallion reconciliation report.

### Ops Layer (Mapping, Quality & Reconciliation)

- Stored in the BigQuery dataset **`acn-uki-ds-data-ai-project.ops`**.
- Contains:
  - **`mapping_input`** — dbt seed; authoritative source-to-target mapping sheet (32 rows)
  - **`relationship_definitions`** — dbt seed; all PK/FK relationships (37 rows)
  - **`medallion_layer_mapping`** — dbt model built from `mapping_input` seed with `layer_order` and `is_implemented` flags
  - **`gold_data_quality_report`** — dbt model; PK / FK / null-check results across all six Gold entities
  - **`medallion_reconciliation_report`** — dbt model; Bronze→Silver and Bronze→Silver→Gold row reconciliation (32 rows)

## Validation Inputs

### 1. `gold_data_quality_report`

`acn-uki-ds-data-ai-project.ops.gold_data_quality_report`

Use this table to identify outstanding primary-key, foreign-key, and required-value issues in the Gold layer. Interpret `check_status` as follows:

| `check_status` | `check_type` | Meaning & Action |
|---|---|---|
| `FAIL` | `PRIMARY_KEY` | The primary key on the Gold entity named in `table_name` is null or duplicated. Trace the mapping from Bronze → Silver → Gold using `medallion_layer_mapping` to find where the key is generated or joined incorrectly. |
| `FAIL` | `NULL_CHECK` | A required column (`checked_columns`) in the Gold entity (`table_name`) is null or blank. Trace the column back through the Silver `SAFE_CAST`/audit logic to Bronze to confirm whether the source value, a cast failure, or a join produced the null. |
| `FAIL` | `FOREIGN_KEY` | A non-null value in `checked_columns` on `table_name` has no match in `reference_columns` on `reference_table` — an orphaned Gold-to-Gold foreign key. Validate the join logic in the Gold dbt model and the relationship defined in `medallion_layer_mapping` / `relationship_definitions`. |

### 2. `medallion_reconciliation_report`

`acn-uki-ds-data-ai-project.ops.medallion_reconciliation_report`

Use this table to confirm that every row is transferred correctly from Bronze to Silver, and end-to-end from Bronze through Silver to Gold. Interpret `reconciliation_status` as follows:

| `reconciliation_status` | `reconciliation_scope` | Meaning & Action |
|---|---|---|
| `FAIL` | `BRONZE_TO_SILVER` | `source_count` (Bronze) does not equal `intermediate_count` (Silver) for `source_table`, or `missing_in_intermediate` / `duplicate_intermediate_keys` > 0. Investigate the Silver dbt model for `source_table` for dropped rows, failed `SAFE_CAST`s, or duplicate primary keys. |
| `FAIL` | `BRONZE_TO_SILVER_TO_GOLD` | `source_count`, `intermediate_count`, and `target_count` do not all match, or any missing/duplicate key count > 0. Investigate the Gold dbt model for `target_table` to confirm every Silver business key produced exactly one Gold output row. |

### 3. `medallion_layer_mapping`

`acn-uki-ds-data-ai-project.ops.medallion_layer_mapping`

Use this as the authoritative source-to-target mapping document. Fields:

| Field | Interpretation |
|---|---|
| `source_layer` / `source_object` / `source_columns` | The upstream layer, dbt model/source name, and columns that feed a given mapping row. |
| `target_layer` / `target_object` / `target_columns` | The destination layer, dbt model name, and columns produced. `target_object` is the canonical dataset name used in Silver and Gold. |
| `primary_key` / `foreign_keys` | The primary key of the target model, and any FK → parent table/column relationships (mirrors `relationship_definitions`). |
| `cast_rules` | The `SAFE_CAST` target data type applied per column when moving Bronze → Silver. |
| `join_rules` / `aggregation_rules` | The SQL join conditions and aggregation logic applied when building a Gold entity from Silver models. |
| `dq_rules` / `audit_rules` | The data-quality checks and audit/lineage columns required at that layer. |
| `output_dataset` / `dbt_model` / `implementation` | The BigQuery destination dataset, the dbt model name under `models/`, and the materialisation type (`table`, `view`, or `incremental`). |

## Validation Rules

Validate all datasets, mappings, and SQL against the following rules:

1. Source-to-target mappings must match the `medallion_layer_mapping` specification.
2. Every `PRIMARY_KEY` or `NULL_CHECK` `FAIL` in `gold_data_quality_report` must be traced from source through Silver to Gold and remediated.
3. Every `FOREIGN_KEY` `FAIL` in `gold_data_quality_report` must be resolved by correcting the join or the underlying relationship definition.
4. Every `FAIL` in `medallion_reconciliation_report` must be investigated until `source_count`, `intermediate_count`, and `target_count` reconcile with zero missing or duplicate keys.
5. Table and column names must match `target_object` / `target_columns` in `medallion_layer_mapping`; Silver preserves Bronze names; Gold entity names must match the six defined canonical entities (prefixed `gold_`).
6. Source lineage must be maintained throughout via `audit_source_system`, `audit_source_table`, `audit_record_hash` (Silver) and `gold_entity_name`, `gold_record_hash` (Gold).
7. All date and datetime columns must be converted to `DATE` or `TIMESTAMP` in the Silver layer per `cast_rules`.
8. Data types must remain consistent between Silver and Gold for every reused column.
9. Audit columns (`audit_*`, `dq_*`) must be added consistently across every Silver model; audit columns (`gold_*`) must be added consistently across every Gold model.
10. Gold-layer unions across multiple source systems (if introduced) must only occur when schemas are fully aligned: identical column names, identical column order, compatible data types.
11. Validate that all required attributes are propagated from Bronze to Silver and then to Gold without being silently dropped.
12. Ensure no required columns are dropped during transformations; validate against `cast_rules` in the Silver model and the mapping sheet.
13. Flag any missing, incorrect, duplicate, or unmapped attributes using `gold_data_quality_report` and `medallion_reconciliation_report`.
14. Never remove the `audit_*` / `dq_*` columns from Silver models or the `gold_entity_name` / `gold_created_ts` / `gold_record_hash` columns from Gold models; these are standing platform requirements, not optional additions.

## SQL & dbt Standards

All SQL generated must:

- Follow the `medallion_layer_mapping` specification.
- Be implemented as **dbt models** (`.sql` files under `models/silver/`, `models/gold/`, or `models/ops/`); BigQuery SQL only — no Spark SQL or PySpark.
- Use **explicit column selection**; never use `SELECT *` in production models (only permissible in the `bronze` CTE at the top of a Silver model).
- Use **`SAFE_CAST`** (never bare `CAST`) when converting Bronze columns to typed Silver columns, so a bad value produces a detectable `NULL` instead of failing the job.
- Use meaningful table and column aliases.
- Use consistent formatting and indentation.
- Use **CTEs** where appropriate for readability — the standard Silver CTE chain is `bronze → typed → quality → final SELECT`; Gold models use per-entity aggregation CTEs.
- Fully qualify tables and columns (`project.dataset.table`) when cross-dataset references are needed.
- Reference Bronze sources via `{{ source('bronze', '<table>') }}` and Silver models via `{{ ref('silver_<table>') }}`.
- Use **`{{ config(materialized='table') }}`** for Silver and Gold models; ops models may use `view` unless query cost is a concern.
- Include audit and lineage columns where required at every layer.
- Maintain consistent naming conventions: Silver models are prefixed `silver_`; Gold models are prefixed `gold_`; ops models have no prefix.
- Use dbt macros (`generate_schema_name`, `reconcile_layer`, `dq_check`) for schema routing, reconciliation, and quality checks.
- Ensure all joins follow relationships documented in `relationship_definitions` / `medallion_layer_mapping`.
- Use `ON` predicates rather than `USING` in multi-source Gold joins where column name collisions may cause BigQuery ambiguity.
- Produce production-ready, readable, and maintainable SQL.

## Schedules

No schedules are currently configured — all builds have been triggered manually via dbt CLI. Recommended follow-up:

1. **dbt Cloud** (preferred): Create a dbt Cloud job with the `dbt build` command and chain runs in dependency order:
   - Job 1: `dbt build --select silver.*` (after Bronze source refresh)
   - Job 2: `dbt build --select gold.*` (after Silver completes)
   - Job 3: `dbt build --select ops.*` (after Gold completes — runs DQ + reconciliation)

2. **BigQuery Scheduled Queries** (alternative for ops reports only): Schedule `gold_data_quality_report` and `medallion_reconciliation_report` as BigQuery scheduled queries to run immediately after every Gold refresh.

3. **GitHub Actions** (CI): Add a workflow that runs `dbt build --profiles-dir .` with a service-account key secret on every pull request to `master`, to catch regressions before merge.

# Install Python 3.12 virtual environment with dbt-bigquery
python3.12 -m venv dbt_venv
source dbt_venv/bin/activate          # Windows: dbt_venv\Scripts\activate
pip install dbt-bigquery==1.12.1

# Authenticate with GCP
gcloud auth application-default login
gcloud config set project acn-uki-ds-data-ai-project

# Install dbt packages
dbt deps

# Verify connection
dbt debug

# Load seed mapping tables into ops dataset
dbt seed

# Build full pipeline: all Silver + Gold + Ops models + all tests
dbt build

# Generate and serve documentation
dbt docs generate
dbt docs serve

## Objective

Validate that the correct source attributes, entities, and datasets are propagated from Bronze through Silver to Gold, ensuring the final canonical credit-card model is complete, accurate, traceable, fully compliant with `medallion_layer_mapping`, and free of primary-key, foreign-key, null, and row-reconciliation failures as reported by `gold_data_quality_report` and `medallion_reconciliation_report`.
